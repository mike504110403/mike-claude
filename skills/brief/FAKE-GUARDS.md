# 假防護型錄（brief 驗收標準/紀律欄的參照）

派工退件原因裡，**「假防護／假測試」遠多於「功能沒做對」**——測試全綠但守不住。寫 brief 與驗收時對照下列形狀。

## 形狀

**A. 參照物與被測物同源** —— 測試拿的是待驗證的那個東西自己，它壞掉時測試跟著一起壞。
- 測試自己重算一份公式去比對，從沒呼叫過生產路徑
- 把 SQL 常數逐字抄一份，再斷言常數等於抄本；「抽 const 供測試斷言」是同病的鏡像變體——const 與 Up()/Down() 實際 Exec 沒有機制綁在一起
- 期望值去讀被測的那個變數（刪一欄時期望值跟著縮水，永遠不紅）
- 子字串沒有邊界：`"config_valX"` 包含 `"config_val"`、`default:0` 是 `default:0.5` 的前綴
- 「動態算期望值」與實作同一條式子（`== all_events()[0].id` vs 實作同式）——規則在該檔恆真

**B. 涵蓋範圍有縫** —— 條件看起來涵蓋了，實際有個洞。
- SQL 三值邏輯：`WHERE x <= 0` 抓不到 NULL → 全表沒填時自檢回報「乾淨」（反向失敗，比漏抓更糟）
- `if got != want {Fatalf}` 之後的 `if got == old` 是死碼，卻自稱有在檢查
- 正確性只活在 struct tag / 宣告裡，沒有行為測試——宣告只能當快速護欄，**行為必須用行為測**

**C. 哨兵的參照物與被測物「碰巧相等」** —— 拿 `math_odds == odds_limit` 的列當「沒被修改」的證據，但那種列在任何實作（含錯誤實作）下都不變。有效哨兵必須挑**嚴格不等**的列，且先斷言該列的前提值。

**D. 保護落在錯的連線上** —— `db.Exec("SET SESSION ...")` 與後續 DDL 各自從連線池取連線；要用 `db.Transaction` 釘在同一條。測試端用 `MaxIdleConns(0)` 數整趟開了幾條連線才有鑑別力（`MaxOpenConns(1)` 會假綠）。

**E. 防護本身沒有被測** —— 純防禦性的那行（如 `Round(3)`）刪掉全套仍綠。**加防護時要問「刪掉它哪個測試會紅」，答不出來就是還沒測。**

**F. fixture 太薄 → 斷言範圍小於宣稱範圍** —— 測「只碰兩個欄位」但 fixture 只填 2/5 欄。修法：fixture 填滿呼叫端實際會填的所有欄位，斷言「覆寫該改欄位後整個 struct DeepEqual」。

**G. 變異腳本本身沒生效，卻報「存活」** —— argv 沒傳進去、regex 沒對上、縮排不符……變異沒套上，測試自然綠。**每個變異植入後先確認檔案內容真的改變**（`git diff` 有輸出）再跑測試；還原不可用 `git checkout -- <file>`（會洗掉未 commit 的工作，bash_guard hook 會攔下確認），用 `cp` 備份還原。

**其他恆真式**：對編譯期已保證的事寫執行期測試；對「天生不可能發生」的路徑斷言；log 斷言斷在永遠不會被寫入的事件上；失敗路徑的觀察點被錯誤顯示機制覆寫遮住（觀察點要選覆寫範圍之外的鄰居）。

## 寫 brief 時明寫三件事

1. **驗證對象必須獨立於被驗證對象。** 不接受「測一份複製品」「拿常數對照常數」；必要時起一次性 docker DB 用行為測。
2. **變異驗證要指定「必須紅」的具體變異體**，並要求工人回報實際輸出。不改變外部行為的變異，綠燈是正確答案（equivalent mutant）。變異清單**按守護目標列、逐規則列全、枚舉全部消費者與同類方法**（含 A/B/A∪B 拆分時的聯集本身）。
3. **寧可回報「這條沒測到」也不要一條假綠的測試。** 明確授權工人說「切不出 seam」。

## 驗收端自守

- 變異體先確認**落在程式碼行而非註解行**、且真的落下去了（G 條）。
- 驗「純註解改動」用 AST 比對，不要 grep 濾 `//`。
- 不拿 seed / 初始值當現況的代理（只在全新安裝時相等）。
- 工人的變異證明要檢查是不是「自首型」（變異體順手加了配合測試的 log 才紅）——用「最自然的犯錯寫法」重做變異。
- 大腦自己抽查時選「工人沒做過的變異」。
- **判準：問「bug 存在時這條斷言會不會紅」**——會紅就不是假防護（頂多診斷品質問題），這個詞保留給「測不到」。

## 給大腦的教訓

brief 裡指定的哨兵值、期望值、變異預期，**大腦自己也常寫錯**。brief 要明寫「這幾個期望值請自己實跑確認，不要照抄我寫的」，並明確授權工人推翻；工人回報「規格與實測不符」時，先自己驗一次再決定——通常工人是對的。指定具體斷言前，先想一個「最自然的犯錯寫法」並確認該斷言會紅；想不出來就只寫「要守住什麼行為」，讓工人設計斷言並附變異證據。JS 隱式轉換、觸發時機這類判斷式先 `node -e` 跑一次真值表再寫進 brief。
