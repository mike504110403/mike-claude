# Brief 模板

每份 brief 固定八個欄位，照順序填。工人只憑這份文件獨立完成，不中途回來問；寫完自檢：「一個沒看過這個專案的人，只讀這份 brief 能不能動工？」

```markdown
## 目標
<一句話說清楚做什麼、為什麼>

## 範圍
<明確列出可以動的檔案；範圍外的檔案一律不碰>

## 工作環境
<工作目錄 = worktree 絕對路徑（大腦先依 /feature-flow 開好）、分支 = `wt/<feature>/<task-slug>`。
 所有指令在該路徑下執行；commit 全留在該分支；不 merge、不 push、不切分支、不動 worktree 之外的目錄>

## Seam（測試邊界）
<在哪個公開介面上驗證行為 — 函式簽名 / API endpoint / CLI 指令。
 測試只寫在這裡議定的 seam 上，不測內部實作細節。
 至少一條測試走「真實組裝路徑」（App 根 widget / 真組態 / 真儲存的整合流程），
 不能全部單元隔離；seam 的注入點不得在測試裡釘成常數，把待測的重讀/轉移邏輯遮掉
 （2026-07-30 兩波退件教訓：gate 誤放行與 tile 自隱藏都因此漏網）>

## 驗收標準（可執行）
<盡量寫成「跑這個指令要看到什麼結果」：
 - `go test ./internal/foo/...` 全綠，含新增的 <行為> 測試
 - `npx vue-tsc --noEmit` 無錯誤
 寫不成可執行的（如文案、樣式），寫成可肉眼查核的具體描述>

## 紀律
<引用適用的 skill：
 - 功能 / 修 bug 帶測試 → 測試紀律遵循 /tdd（red-green、只測 seam、垂直切片）
 - bug 類任務 → 流程遵循 /diagnosing-bugs（先重現再動手，修完留回歸測試）
 - 模組介面設計 → 參考 /codebase-design（deep module）
 - Vue 專案任務 → 紀律遵循 /vue-dev（script setup + TS、只用 Pinia、走既有 axios 封裝、跟隨專案 CLAUDE.md），驗收標準必含 `vue-tsc --noEmit`（或內含它的 build）實際輸出
以下三條為常備紀律，每份 brief 原文照抄（第三條 2026-08-05 起，防「做一做撈既有問題出來處理」的 scope creep）：
 - 範圍外既有問題一律不處理：任務途中發現的既有 bug、壞味道、lint 錯誤、過期依賴…只要不在本 brief 範圍內，一律不修、不順手重構，記下來放進回報的「順路發現」清單即可。唯一例外：該問題直接擋住驗收標準達成——此時停下用 SendMessage 回報，等指示，不得自行擴大範圍。
 - 非同步失敗路徑一律要處理：任何 await 使用者操作（存檔/登入/刪除）失敗時，UI 必須解除 loading 並浮出錯誤，不得 fire-and-forget、不得讓例外流成 uncaught async error；每條破壞性/寫入操作至少配一條失敗路徑測試。
 - 狀態快取生命週期要交代：用狀態框架（Riverpod 等）時寫明快取何時失效（watch vs read、invalidate 時機）；換帳號、登出、跨頁回訪、跨日不得看到過期資料。>

## 禁止事項
<此任務明確不做的事：不碰的檔案、不升級依賴、不順手重構、不 push …>

## 回報格式
done 時必附，缺一視同未完成：
1. commit hash + `git diff --stat`
2. 測試 / typecheck **實際執行輸出**（不是「已通過」三個字）
3. 驗收標準逐條對照：達成 / 未達成 / 部分達成＋原因
4. **規則張力與偏離清單**：brief 規定與實際需求衝突、或你偏離 brief 字面的每一處，寫明張力是什麼、你怎麼解、為什麼（**無則明寫「無」**）。發現張力當下就該 SendMessage 回報，不准自行解掉再事後補記。
5. **順路發現清單**：範圍外既有問題逐條列出，只列不修（**無則明寫「無」**）。
6. 完成時**必須用 SendMessage 主動送出完整報告**，idle 通知不算回報；送出後未獲回應就重送並標明重送。
```

## 給大腦的規則

- **Seam 先議定**：brief 裡沒寫 seam 就不派工。範圍不清楚時先探索或問 Mike，不把模糊丟給工人。
- **reviewer / 探路員的派工也要帶回報條款**（2026-08-05，第三次同型）：上面回報格式第 5 條（「必須用 SendMessage 主動送出完整報告，idle 通知不算回報」）只寫在工人 brief 模板裡，但 code-reviewer / security-reviewer / 探路員的 prompt 是大腦另外手寫的，**常常漏掉這條**，結果一路送 idle 不送結論、大腦每次手動催。派任何子代理（含 reviewer、探路員）都要把那句原文帶上；reviewer 還要額外明寫「沒發現問題也要回空陣列 + SendMessage 說明審了哪些重點項，『沒問題』也是要交付的結論」。SendMessage 字串訊息**必帶 `summary` 參數**（缺了會報錯卡死，小模型工人不會自行重試）；回報段唯一合法句式就是上面那句祈使句——出現過大腦寫「直接輸出報告結束回合」，等於指示對方把報告寫在大腦看不到的地方。
- **中途改規格會跟工人搶回合**：SendMessage 進 inbox，工人跑完當前回合才讀。規格變更盡量等工人 idle 再發；非發不可時第一句寫「本則取代先前關於 X 的全部指示」，並直接給要退掉的 `git revert <hash>`（它多半已 commit）。工人回「這我已經做完了」通常是讀到舊訊息——列差異點比爭論快。驗收一律看檔案實際狀態與 commit 內容（`git show <branch>:<path>`），不信回報宣稱的規格版本。契約類補充在派工當下寫進 brief，不邊做邊追加。
- **引用外部文件的斷言前，先分辨它是敘述句還是交辦清單**：checklist 未勾選＝沒做過；「只改本體即可」是在描述改動幅度、不是禁令。從文件抄進 brief 的約束要與本 brief 其他欄位逐條對照查互斥（互斥自檢適用所有輪次，不只修正輪）。
- **既有問題一律不處理（Mike 裁示 2026-08-05）**：工人/reviewer 順路發現的既有問題，完成回報第 5 點列一行即可——不追問超過一次、不排案、不讓工人動手，只有 Mike 點名才處理。「既有」的判準：不動我們的 diff 它也一樣壞；本波改動觸發或流經的路徑仍要修。
- **假防護型錄**：寫「驗收標準」與「紀律」欄前先讀 [FAKE-GUARDS.md](FAKE-GUARDS.md)——退件最大宗，各種形狀與防線都在裡面。
- **驗證指令要先自證**：寫可執行驗收指令前先讀 [VERIFICATION-TRAPS.md](VERIFICATION-TRAPS.md)——本機工具陷阱（ugrep、gofmt、zsh 分詞、vue-tsc 設定層中止）與控制檔紀律。
- **變異證明要枚舉消費者**（2026-08-04，同日 3 退件教訓）：驗收的「變異必紅」必須逐一列出受防護資源的**全部消費者**與**全部同類方法**（例：翻譯表的消費者 = 卡牌 + 敵人 + UI 字串；getter 防污染 = 四個 getter 各一條），且證明必須在 brief 文件指定的指令下成立、不得依賴未寫進 brief 的額外步驟。禁用「加一條測試」這種單數寫法——工人會字面滿足。
- **brief 裡的「數量」一律標成僅供參考**（2026-08-06，同一輪四次全部低估）：大腦盤點清單時數字錯了四次（19→21、5→7、7→9、1→4），成因一致——**估的時候只看「字面含關鍵詞」的**。清單類 brief 一律寫「**數量僅供參考，以呼叫鏈追蹤結果為準**」，並點名兩個必漏的盲點：
  1. **同函式／同錯誤族內字面不含關鍵詞的**（例：返點驗證函式裡的「获取游戏分类失败」，漏它會讓同一支函式一半改一半沒改）
  2. **間接路徑上的**（例：repo 層函式經中間層才回到 handler 原文輸出：`GetMaxSubnateLimitRateByCategory` → `ApplyRebateUpdate` → `services/account.go` → 後台）
  判準寫成「**這個 error 最終有沒有走到 `FailWithMessage`／`OkWithMessage`**」，不是「字面像不像」。光寫「以追蹤為準」不夠，要指名會漏在哪才可操作。
- **失敗路徑測試的觀察點要避開錯誤顯示的覆寫範圍**（2026-08-06 sanity-toll P2b 複審教訓）：UI 失敗態若用「覆寫該元件文字」呈現（如把該列按鈕蓋成「存檔失敗」），該元件就不能同時當「狀態有沒有還原」的觀察點——錯誤 UI 本身成了新的「參照物不獨立」，狀態邏輯算出什麼都被蓋掉、測試恆綠。斷言要挑不被覆寫的鄰居（另一列、列外 label、衍生行為）。同輪連帶：對「天生不可能發生」的路徑斷言（如對無 make_dir 的不存在目錄斷言 file_exists 為假）是恆真式，不算覆蓋。
- **外部輸入要標信任邊界**：brief 若涉及讀取外部來源（manifest、設定檔、API 回應），必須明寫「此輸入不受信」與對應的驗證要求（路徑 containment、型別、大小），否則工人預設信任它。
- **變異清單逐規則列全，不抽樣**（2026-08-04 Wave 2 兩次同型教訓）：規則規格裡的每一條規則，變異清單都要有對應的「可觀察後果」條目——按規則列，不是按欄位或按 op 列。抽樣列（列了 reset 沒列 absorption、列了七個 op 沒列棄手牌）的缺口 reviewer 兩度用「刪掉整段實作仍全綠」抓到。
- **規格引用的欄位要先對照真實 schema**（2026-08-04 教訓）：brief 規則寫到某欄位/名稱（如「掃描 status 名」），動筆前先開真實資料檔確認它存在；引用不存在的欄位會逼工人自行發明語意（推論規則→死守衛+語意反轉）。
- **修正輪 brief 的禁止事項要逐條對照修正項查互斥**（2026-08-04 教訓：「顯示錯誤」×「不新增翻譯 key」打架，工人硬寫英文字串）；並在 brief 紀律加一句：規則互斥或無法同時滿足時，停下用 SendMessage 回報，不得自行取捨。
- **清除/重置類任務要寫「清除後不變式」**（2026-08-04 帳號隔離退件教訓）：不只列清除清單，還要列清完後必須維持的狀態（如「重啟後資料仍為空」），並要求工人盤點所有會把資料寫回來的機制（匯入器、快取、同步、重試），配重啟劇本測試。
- 驗收標準寫不出可執行形式時，回頭檢查是不是任務本身還沒想清楚。
- 一份 brief 一個工人一個目標；要兩個工人配合的，拆成兩份 brief 並在範圍上互斥。
