# 驗證指令陷阱（寫可執行驗收標準前的參照）

**驗證指令本身也可能是假的**。宣告「乾淨／通過」之前，先用一個**確定含目標特徵的控制檔**跑同一條指令，確認它真的測得到；測不到控制檔的指令，掃真實檔案回報 0 沒有任何意義。

## 本機工具陷阱（實測記錄）

1. **`gofmt` 會改 doc comment 內容**：Go 1.19+ 把 `''` 轉成 U+201D `”`。doc comment 裡永遠寫不出 `''`——只能換寫法（改引函式名或文字描述）。涉及會被工具重寫的檔案，驗證要**跑過格式化工具之後再驗一次**（冪等性檢查）；整檔 sha256 前後比對比計數為 0 更強。
2. **這台機器的 `grep` 是 ugrep，不是 GNU grep**：`grep -P '\xNN'` 對確定含該位元組的檔案回報 0；多檔搜尋時**行號會錯、還會漏同行匹配**。可靠寫法：`LC_ALL=C grep -cF "$(printf '...')"`、`xxd -p | grep -o`。**報告裡的 `檔案:行號` 一律以 Read / `sed -n` 讀出來的為準**，grep 只用來找「哪個檔案有」。
3. **zsh 不對未加引號的變數分詞**：`PKGS="./a/... ./b/..."; go test $PKGS` 整串當一個參數，測試根本沒跑、批次變異全報「綠」。要用陣列 `"${PKGS[@]}"` 或 `${=PKGS}`。徵兆：**對照組也一起異常**（「還原 → 0 個套件 ok」= 輸出是空的）。
4. **`vue-tsc` 遇設定層錯誤會中止，完全不做型別檢查**，錯誤數看起來像「只有既有問題」。錯誤全是 `TS6504`/`TS5xxx`/`TS18003` 這類設定層代碼（而非 `TS2xxx`）時，先懷疑它沒開始檢查（已有專案實測中招，該專案 CLAUDE.md 有標注）。**「錯誤數維持 baseline」這種驗收寫法特別危險**——工具中止時那個數字在程式碼壞掉時也不會變。
5. **「build 過了」≠「型別過了」**：vite/esbuild/babel 只剝型別不檢查。

## 紀律

- 把 typecheck 寫進 brief 驗收標準前，**先植入一行必錯的型別賦值**證明該指令在該 repo 測得到。
- 驗證「某特徵不存在」時，先造控制檔證明指令測得到，再掃真實檔案。
- **變異腳本第一項必放「必紅控制組」**（故意改壞一個一定有測試守著的地方）；控制組沒紅 = 腳本壞了。批次結果全部同方向，永遠先懷疑量測工具。
- 變異要**編得過**才算數：編譯失敗的紅燈來自編譯器，證明不了測試守得住。
