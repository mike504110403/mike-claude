# 驗證指令陷阱（寫可執行驗收標準前的參照）

**驗證指令本身也可能是假的**。宣告「乾淨／通過」之前，先用一個**確定含目標特徵的控制檔**跑同一條指令，確認它真的測得到；測不到控制檔的指令，掃真實檔案回報 0 沒有任何意義。

## 本機工具陷阱（實測記錄）

1. **`gofmt` 會改 doc comment 內容**：Go 1.19+ 把 `''` 轉成 U+201D `”`。doc comment 裡永遠寫不出 `''`——只能換寫法（改引函式名或文字描述）。涉及會被工具重寫的檔案，驗證要**跑過格式化工具之後再驗一次**（冪等性檢查）；整檔 sha256 前後比對比計數為 0 更強。
2. **這台機器的 `grep` 是 ugrep，不是 GNU grep**：`grep -P '\xNN'` 對確定含該位元組的檔案回報 0；多檔搜尋時**行號會錯、還會漏同行匹配**。可靠寫法：`LC_ALL=C grep -cF "$(printf '...')"`、`xxd -p | grep -o`。**報告裡的 `檔案:行號` 一律以 Read / `sed -n` 讀出來的為準**，grep 只用來找「哪個檔案有」。
3. **zsh 不對未加引號的變數分詞**：`PKGS="./a/... ./b/..."; go test $PKGS` 整串當一個參數，測試根本沒跑、批次變異全報「綠」。要用陣列 `"${PKGS[@]}"` 或 `${=PKGS}`。徵兆：**對照組也一起異常**（「還原 → 0 個套件 ok」= 輸出是空的）。
4. **`vue-tsc` 遇設定層錯誤會中止，完全不做型別檢查**，錯誤數看起來像「只有既有問題」。錯誤全是 `TS6504`/`TS5xxx`/`TS18003` 這類設定層代碼（而非 `TS2xxx`）時，先懷疑它沒開始檢查（已有專案實測中招，該專案 CLAUDE.md 有標注）。**「錯誤數維持 baseline」這種驗收寫法特別危險**——工具中止時那個數字在程式碼壞掉時也不會變。
5. **「build 過了」≠「型別過了」**：vite/esbuild/babel 只剝型別不檢查。
6. **裸 `npx <工具>` 在沒有 `node_modules` 的目錄會靜默從 registry 抓最新版**：新 worktree 未裝依賴時 `npx vue-tsc` 跑的是 6.x 而非專案鎖定的 0.38.x，同一份程式碼「2 條警告」vs 實際「697 行錯誤」（2026-08-12 實測）。驗證工具一律 `pnpm exec` / `./node_modules/.bin/`，先確認執行檔存在；worktree 開好先依 lock 檔裝依賴。

## 紀律

- 把 typecheck 寫進 brief 驗收標準前，**先植入一行必錯的型別賦值**證明該指令在該 repo 測得到。
- 驗證「某特徵不存在」時，先造控制檔證明指令測得到，再掃真實檔案。
- **變異腳本第一項必放「必紅控制組」**（故意改壞一個一定有測試守著的地方）；控制組沒紅 = 腳本壞了。批次結果全部同方向，永遠先懷疑量測工具。
- 變異要**編得過**才算數：編譯失敗的紅燈來自編譯器，證明不了測試守得住。
- **SKIP 也是綠**：需要外部資源的測試（真 DB／真 API／環境變數開關）在資源不存在時多半 `t.Skip`，`go test` 照樣印 `ok`。**「測試全綠」不等於「那條保證被驗過」**——實測案例：釘住 migration 冪等性的四支 real-MySQL 測試在沒有 DSN 時全部 SKIP，綠燈完全沒執行到「重跑不動既有列」這條保證；reviewer 起一個一次性 MySQL 容器補跑才真的驗到。判準：**驗收前先看 `-v` 輸出裡有沒有 SKIP**，關鍵保證若落在被 SKIP 的測試上，就是還沒驗；要嘛把資源起起來，要嘛在回報明寫「這條沒驗到」。
- **變異腳本要自我驗證「目標存在」**：`str.replace` / `sed` 找不到目標是**靜默 no-op**，跑出來的綠燈會偽裝成「測試不夠力」甚至「這裡不需要測試」——比漏測更糟，因為它導出**錯誤結論**。腳本開頭就 `assert old in s`（或 `grep -q` 前置檢查），套不上當場炸。同日實測兩起：搜尋字串少抄同行前半段（`\t52: 180,` vs 實際 `\t51: 75, 52: 180,`）、憑印象寫的識別字與實際不符（`strings.Join(parts, ",")` vs 實際 `strings.Join(numStrs, ",")`）。
- **乾淨樹上 `git stash` 是 exit 0 的 no-op，`&&` 擋不住，後續 `stash pop` 會彈出別人的舊 stash**（repo 的 stash 堆疊是跨 worktree 共用的）：拿 stash 往返做「改動前 baseline」比對，若當下樹其實是乾淨的（改動已 commit），stash 沒存東西、pop 卻把歷史 auto-stash 或他人 WIP 砸進工作區。2026-08-19 同日兩起（工人在 platform、大腦在 backend 各踩一次）。正確做法：**baseline 比對用另一個 worktree、`git show <ref>:<path>`、或 `git diff <ref>` ——不用 stash 往返**；非用不可時先 `git stash list` 記下既有條目數、stash 後確認真的多了一條才准 pop。誤 pop 的復原：把彈出的內容 `git stash push -m "restash: ..."` 原樣存回，不擅自 apply 或丟棄（那是別人的工作）。
- **修「量測誤報」時必附「量測仍活著」的反向斷言**：把恆真的斷言改成量自己的 ledger 之後，同一案再加一條「ledger 至少有 N 筆」（N＝當下已知下界），否則 ledger 空掉時原斷言又變恆真——單向修法只是把假防護換一個方向（2026-09-15 mutate-batch 案，同一工程連犯兩次）。
- **測試起的行程三規**：(a) 比對與清理用**本案唯一字串**（如 `$D/i3.marker`）做 `pgrep -f`／`pkill -f`，不用通用 pattern——全域 pattern 會誤判、誤殺別的 session 的行程；(b) 無論紅綠都收屍（`wait`，或 `kill -9` 後 `wait`），不留孤兒；(c) 所有等待設上限（迴圈計數或 `timeout`），裸 `wait` 在被測程式吃掉 SIGTERM 時會無限卡死——2026-09-15 實測整個 session 被 kill -9 才停。
