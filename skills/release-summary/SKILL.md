# /release-summary — 待更新清單格式

清單是給更新／運維的人看的：只講要做什麼、上什麼、使用者看得到什麼，技術細節等追問再給。

## 盤點（先取事實，不憑記憶）

1. 依 `~/.claude/PROJECTS.md` 解析該專案群全部 repo 路徑。
2. 每個 repo `git fetch` 後跑 `git log --oneline --no-merges origin/<正式分支>..origin/<來源分支>`（彩票：`origin/m5-prod..origin/online`）。
3. 檢查正式分支上刻意擋下的 revert（`--grep='^Revert'`，扣掉已有 `Reapply` 的）；這些功能不會跟著合併上去，要在回覆末尾補一句。
4. 部署前提、順序從各功能的 memory 和 repo 的 `.claude/wip.md` 取。
5. Mike 說要排除的項目（例如開獎中心）不列。

## 輸出格式（固定）

```
**更新前操作：**
1. …
2. …

**需要更新的服務：** repo-a → repo-b → repo-c、repo-d

**更新內容：**
1. …
2. …
```

規則：

- **更新前操作**：有編號。運維要先手動做的事、要先查的資料庫條件、更新時間窗等限制都寫在這裡。沒有就整段省略。用白話寫要做什麼、為什麼要做，SQL 內文不要貼。
- **需要更新的服務**：一行內寫完，用 repo 名稱和 `→` 表示順序，順序不拘的用 `、` 並列。不條列，也不加括號或任何說明。
- **更新內容**：有編號。一個功能一點，只寫功能、從使用者／營運的角度描述。不寫 commit hash、檔名、API、表名，也不寫 test／docs／bruno 這類不影響功能的 commit。
- 三段之外最多再加一兩行，用來寫被刻意擋下的功能和待裁示的事項，然後結尾說明下一步（例如「說『推 m5-prod』我就走 /ship」）。
