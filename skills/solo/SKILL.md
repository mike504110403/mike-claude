# /solo — 中型單線直改

/quick 的放寬版：範圍大一號，換一道 code-reviewer 守備。免 brief、免 worktree、免派工。

## 入選標準（全部成立才進）

- 超出 /quick（>3 檔，或行為變更中等）
- 單一意圖：一句話講得完要做什麼，不含第二件事
- 技術路線清楚，不需要探索或選型
- 單 repo；預估改動 ≤8 檔

## 硬排除

與 /quick 同清單（依全域 CLAUDE.md 不變式），命中一律至少 /feature。

## 流程

1. **宣告**：第一句「走 /solo，因為…；改動面：後端／前端／前後端」。驗證義務照全域「改動面 × 驗證義務」矩陣。
2. 依 /feature-flow 階段一開需求 worktree（主 checkout 恆 dev 不直改），大腦在需求 worktree 裡**直接改**。
3. **自驗**：走 /verify 的直改裁剪（自我 diff 過範圍＋照改動面矩陣親跑證據）。
4. **Review**：走 /review-chain（對照物 = 宣告文擴寫的任務描述；打回修完重跑全鏈）。
5. 改動涉及 API 且專案有 `bruno/` → 照跑 /bruno-sync。
6. Commit 後停下。

## 跳線

- 改到第 9 個檔案、或冒出第二條意圖 → **停手**、宣告「升級 /feature，因為…」、帶著已知情報走。
- 冒出未決技術選型 → 宣告升級 /mega。
- 改的過程發現行為壞掉但根因不明 → 宣告轉 /bug。
- 發現其實 ≤3 檔且一眼見底 → **先問 Mike** 才降 /quick。

## 回報格式（一段式＋review 結論）

一段話講完：改了什麼＋為什麼＋證據（測試/typecheck/實測輸出摘要），另附一行 review chain 結論（誰審過、結果）。順路發現的範圍外問題列一行「要不要處理？」。
